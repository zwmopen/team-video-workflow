# 远程在线通道设计

## 能否做到

可以。手机使用流量、连接异地 Wi‑Fi，甚至电脑与手机不在同一城市时，电脑面板仍可显示手机在线并完成拖拽投送。

## 推荐架构：三通道，而不是直接暴露电脑端口

通道优先级固定为：

```text
USB 文件传输 → 同一局域网直连 → 端到端加密互联网中继
```

前一条不可用或传送前探测失败时才自动切到下一条。切换通道不生成第二台设备，设备卡片按稳定设备身份合并。

界面统一称为“远程传送”。设备可达但尚未选路时显示“远程”；发送开始后按实际路线显示“远程直连”或“远程中继”，不把 P2P、ICE、STUN、TURN 等实现术语暴露为日常设置。

### USB 通道

- Android 使用 Windows Portable Devices/MTP 写入 `Download/Lark`，不使用 ADB。
- iPhone 使用 Apple Mobile Device 文件共享写入“相册”容器。
- 手机只处于充电或调试接口时仍显示“USB 已连接，待文件传输”，不会冒充可传状态。

### 局域网通道

- Windows 通过 UDP 自动发现手机。
- 文件由电脑直接传到手机。
- 不经过云端，速度最快。

### 云端中继通道

- Windows 和安卓都主动建立出站 HTTPS / WebSocket 连接。
- 云端维护设备在线状态和任务通知。
- 文件由电脑上传到临时对象存储，手机收到命令后下载。
- 下载完成、SHA-256 校验通过后删除云端临时文件。

推荐 Cloudflare 组合：

- Workers：认证、任务 API、临时下载授权。
- Durable Objects：工作区内设备在线状态和 WebSocket 会话。
- R2：图片和视频的短期中转存储。

这种方式不需要公网 IP、不需要路由器端口映射，也不需要电脑开启可被互联网扫描的入站端口。

## 远程路线优先级与备用方案

| 顺序 | 路线 | 用途 | 结论 |
|---|---|---|---|
| 1 | USB | 同一电脑旁的大文件 | 当前正式通道 |
| 2 | 局域网 WiFi | 同一网络内的电脑、手机互传 | 当前正式通道 |
| 3 | WebRTC/ICE 远程直连 | 异地 WiFi、手机流量之间直接传送 | 推荐远程主通道；需要信令和 STUN |
| 4 | TURN 或自建加密 Relay | NAT 穿透失败时兜底 | 推荐远程兜底；需要公网服务 |
| 5 | 已登记电脑中继 | 多台电脑在线时替设备转发 | 可选备用；电脑适合长期中继 |
| 6 | 已登记手机中继 | 特殊情况下临时转发 | 仅前台或充电时允许，默认关闭 |

界面不让用户选择技术路线。发送时自动按 `USB → WiFi → 远程直连 → 远程中继` 探测，真正开始后才显示选中的路线。

### 为什么不让所有手机默认当中继

手机处在运营商 NAT 后面时通常不能接受公网入站连接；iOS 和部分安卓还会冻结后台网络任务。强制手机长期中继会额外耗电、耗流量，并且传一半可能被系统终止。因此电脑可作为稳定中继，手机只在应用前台或充电且用户允许时成为临时中继。

### 可以复用的开源组件

- Syncthing：复用设备证书、发现、TCP/QUIC 直连和 Relay 的设计；不直接承担产品的一次性发送交互。
- coturn：作为标准 STUN/TURN 服务器，为 WebRTC 直连提供穿透与兜底。
- Syncthing `strelaysrv` / `stdiscosrv`：可用于验证自建发现和 Relay 运维，但移动客户端仍需统一适配。
- WebRTC DataChannel：适合异网设备直接传输；大文件需要分片、断点续传、SHA-256 和后台恢复。

Syncthing 的官方 Android 包已停止维护，iOS 没有同一套官方客户端；把完整 Syncthing 运行时直接嵌入会导致 Android、iPhone 6 和 iPhone 12 形成不同产品。项目保留一次性发送交互，底层借用其开源思想与可独立部署的服务。

## 首次登记与配对开关

第一次电脑与手机在同一局域网出现时：

1. 每台设备首次安装生成独立公私钥；私钥不离开设备。
2. Windows 首次在 USB 或局域网看见设备时，由电脑端确认其公钥并登记。
3. 设备第一次通过本机 USB 或同一局域网被发现后，USB、WiFi、远程传送三种方式默认允许；电脑端可在设备右键菜单里分别关闭，关闭结果持久保存。
4. 后续设备在任何网络下用签名挑战登录中继；关闭开关立即撤销该设备的远程会话。

界面不出现地址、令牌或配对码，但“同一套 App”不能替代设备身份校验，也不能让所有安装包共享一个万能密钥。设备列表按稳定公钥指纹合并，因此从 USB/Wi‑Fi 切到流量时仍是同一张卡片。

## 传输策略

```text
发现可写 USB？
├─ 是：电脑 → 手机 USB
└─ 否：发现局域网直连？
       ├─ 是：电脑 → 手机 Wi‑Fi
       └─ 否：该设备已登记且远程开关已打开？
              ├─ 是：电脑 → 临时密文 → 手机
              └─ 否：提示设备离线
```

优先直传，云端只作为异地和移动网络兜底。

## 安全要求

远程通道不能沿用 V2 的“局域网无鉴权”模式，至少需要：

- 每个工作区独立密钥；
- 每台设备独立身份；
- TLS；
- 短时有效的上传/下载授权；
- 文件 SHA-256 校验；
- 临时文件自动过期；
- 支持从电脑端移除丢失的手机。

## 设备组身份与手机互传

电脑是设备组管理员，但所有设备不能共用同一把私钥：

1. 电脑保管设备组管理私钥；每台电脑、Android 和 iPhone 独立生成自己的设备密钥。
2. 首次在可信局域网登记时，电脑为手机公钥签发设备组成员凭证。成员凭证允许电脑到手机、手机到电脑和手机到手机互传。
3. 两台手机互传时验证对方的成员凭证，不要求电脑始终在线，也不复制电脑私钥。
4. 电脑关闭单个通道，只改变该设备的 USB/WiFi/远程许可；撤销设备则发布带版本号的签名撤销名单，中继服务与其他成员都拒绝该设备。
5. 被关闭或撤销的设备在下一次连接时收到明确状态；远程中继可即时执行撤销，离线局域网设备在拿到更新后的撤销版本后执行。

“远程暂时关闭”“设备离线”“已被设备组撤销”必须作为三种不同状态处理，不能都显示成传送失败。

## 为什么不默认使用 Cloudflare Tunnel

命名 Tunnel 可以把电脑服务暴露到公网，但仍需处理固定域名、凭据、在线状态、文件权限和电脑断线恢复。对于“多手机在线列表 + 拖拽投送”，双方都主动连接中继更稳定，也更容易自动切换局域网与移动网络。

## Syncthing 方案评估

Syncthing 的证书设备 ID、全局发现、直连失败后走 relay 的思路值得复用；但它定位为持续目录同步，不是一次性投送。官方 Android 包已停止维护，iOS 也没有同一套官方客户端，因此不能直接嵌入作为三端统一交付通道。项目采用其安全原则和优先直连思想，不把整个 Syncthing 运行时塞进手机 App。

Windows V3.9.1 已加入设备级传送方式设置与登记状态：同一实体只显示一张设备卡，右侧按 USB → WiFi → 远程排列并只显示当前真实可用通道，右键可设置允许的传送方式。Android 0.5.8 与 iPhone 0.5.2 会持久记录首次在局域网发现的本机电脑身份，为后续远程身份升级保留登记关系。

互联网中继仍需要实际可控的 Worker/Durable Object/R2（或等价服务）、设备公钥和密钥轮换。服务尚未部署前，“远程”不会显示为在线通道，也不会假装已经能够异地传送；完成服务部署、三端端到端加密和撤销测试后再点亮。
