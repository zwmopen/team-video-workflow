## 二、端口与发现

| 用途 | 端口 | 协议 | 出处 |
|---|---|---|---|
| 服务端（电脑）监听 | **45835** | TCP/HTTP | `online_gallery_service.py:287` |
| 手机端相册 App 接收 | **45833** | TCP/HTTP | `OnlineService.java:95`、`IncomingTransferService.swift:6` |
| 电脑端信标广播 | **45832** | UDP | `online_gallery_service.py:3651` |
| Windows 中控设备发现 | 45834 | UDP | `main.cpp:121` |

### 信标机制（UDP 45832）
- `BEACON_MAGIC = "ZWMDS2_GALLERY_DISCOVER"`，每 **2 秒**广播一次。
- 目标 = `255.255.255.255` + 本机各网段定向广播（`x.y.z.255`）。
- 载荷：`service` / `type=beacon` / `v=1` / `port` / `url=http://<ip>:<port>` / `ip` / `ts`。
- 同时**应答手机主动探测**（收到含 MAGIC 的报文则单播回信标）。
- 自保护：忽略 `{` 开头的 JSON 与来自本机 IP 的报文（防广播风暴）。
- 每 30 秒刷新本机 IP 与广播目标。

服务端用 `_LanHTTPServer(ThreadingHTTPServer)`，`daemon_threads=True`、`request_queue_size=128`
（默认队列 5 是多手机转圈的根因，DSH-117）。

## 三、成品库扫描

### 3.1 扫描根

```
DEFAULT_LIBRARY_ROOT = "D:\AICode\项目推进\projects\江湖有旅人\主项目\成品库（GPT+本地脚本制作）"
```

⚠️ **这是脚本里的硬编码常量**（`--root` 可覆盖）。**客户端不参与、没有设置界面。**
**改脚本后必须重启 45835 服务才生效**，否则继续跑旧代码且零报错。

### 3.2 只扫两处

1. **`已发送0次（抖音小红书可发）`** 下的一级目录；
   - 若条目名以 **`作品集`** 开头，或 ∈ `("团建游戏", "游戏", "游戏类")` ⇒ **再下钻一层**收集子目录作品；
   - 否则该条目本身作为一件作品。
2. **成品库根目录直出**的一级目录（跳过忽略项后逐个当成一件作品）。

### 3.3 ⛔ 目录结构铁律（沙盒实测，血的教训）

服务端**只扫一层**：根目录的每个非 `_` 开头目录，都被当成「一件作品」交给 `_inspect_work_dir()`。
所以——

| 你想做的事 | 结果 | 实测 |
|---|---|---|
| 根目录建 `杭州/`、`苏州/` 归类 | ❌ **容器被当成一件作品**（顶层无图）⇒ 判废；里面的作品**整批消失** | 3 套 → **0 套** |
| `已发送0次/作品集_杭州/` 归类 | ✅ 归类 + 全部可见 | 3 套 → **3 套** |
| 根目录平铺（每作品一个目录） | ✅ 全部可见，但根目录会堆 467 个目录 | 3 套 → 3 套 |
| 根目录目的地 + 容器自带图文 | ⚠️ 只冒出「杭州」「苏州」两个容器，里面作品仍丢 | 3 套 → 2 套（还是错的） |

**⇒ 成品不能在根目录套中间层。** 要归类只能放 `已发送0次/` 下且目录名以 **`作品集`** 开头。

### 3.4 跳过规则

- 以 `.` 或 `_` 开头的条目一律跳过 —— 这是**隐藏机制**，`_已发送1次`、`_垃圾作品` 等正是靠这个不参与扫描。
- `IGNORED_NAMES` 显式名单（25 项）：各「已发送 N 次」仓位、`归档`、`待制作待补全`、`发布空间`、`_制作中`、`_待补全_单封面作品集` 等。

### 3.5 作品三门槛

| 门槛 | 判定 | 出处 |
|---|---|---|
| ① **有图** | `_collect_images()` 返回空 ⇒ `return None`（**整条不入库**） | `:1865-1867` |
| ② **文案真源** | 只认 **`文案.txt`**；其余 txt（`三平台文案` / `小红书文案`…）**只进检索，不参与下发** | `:1878-1889` |
| ③ **实质字数** | `copy_is_real()` ⇒ 有效长度 ≥ `MIN_COPY_DISTRIBUTABLE = 30` | `:419-421`、`:331` |

`IMAGE_EXTENSIONS = {".jpg", ".jpeg", ".png", ".webp", ".bmp"}`。

`IMAGE_SUBDIR_FALLBACKS = ("产出素材",)` —— 顶层无图时**只回落这一个目录名**。

> ⚠️ **已知未修（2026-09-28）**：图在 `独立引擎产出/` 或 `原素材/` 的 **6 套被判废**
> （479 候选 → 472 下发）。修复 = 元组加这两个名字，472→478。
> **同类 BUG 第三次**（09-21 只看顶层丢 103 套 → 补 `产出素材` → 现在又丢）。
> 全库已有 159 个目录用 `原素材`。
>
> 另：`\u200b_制作中`（目录名带 U+200B 零宽空格）绕过 `startswith("_")` 判定。

### 3.6 缓存与「实时」真相

| 机制 | 周期 | 说明 |
|---|---|---|
| watchdog 轮询 | **60 秒** | 比对 `(路径, mtime)`，有变更才 `scan(force=True)` |
| 列表缓存 TTL | **30 秒** | 手机拉列表超过 30 秒才重扫 |
| `refresh=1` 强制重扫 | 限速 **3 秒**一次 | 入口流量整形 |

⚠️ watchdog **只比目录自身的 mtime** ⇒ 已存在目录**内部**补图（不新增目录项）察觉不到，要等 TTL 30 秒。

**⇒ 新作品从落盘到手机可见：最迟约 60 秒，通常 ≤30 秒。这是「准实时」，不是真实时。**

### 3.7 库存口径（2026-09-28 实测）

- 可发财位候选 **479 套** = `已发送0次` 467 + 根直出 12
- 实际下发 **472 套**（`status.totalWorks` 与 `/api/online/works` 一致）
- **全库含所有隐藏仓位合计 1475 套**，其中 **999 套不在监听范围**
  （`待制作待补全` 459、`_已发送1次` 266、`_垃圾作品` 77、`_待补全_单封面` 69、`_不合格成品` 65…）

> **`_` 开头 = 不参与扫描/维护**，这条约定同时用于成品库和 `docs/_archive/`。

## 四、文案协议

### 4.1 真源

- 下发**只认 `文案.txt`**。`三平台文案.txt` 是早期 Codex 产线遗留，**不是**它的改名版
  （实测库内 145 套两份都有，其中 32 套内容不同）。
- `文案.txt` 为空时回退 `manifest.json` 的 `copy_content`，再回退其 `rawMaterialPath` 下的任意 `.txt`。

### 4.2 标记格式

- 多版本块：`<<<VERSION_START:名>>> … <<<VERSION_END>>>`
- 文件头：`<<<COPY_FORMAT:MULTI>>>`（V4.5）；旧版有 `<<<COPY_FORMAT:2>>>` / `:3`
- 固定平台块：`<<<X_START>>> … <<<X_END>>>`，`X ∈ DOUYIN / XHS / XHS_2 / XHS_3 / WECHAT / HR / GENERAL`
  显示名依次为：规避营销版 / 种草版 / 大纲方案版 / 短文精选版 / 公众号版 / HR决策版 / 参考文案

两端 `PlatformCopyParser` **不硬编码版本名**，版本名由 `<<<VERSION_START:名>>>` 运行时解析，
**按钮顺序 = 文案块顺序**。

### 4.3 V4.5 全系 11 版本（逐字，禁自造）

**现行名（改名后）：**
```
数字爆款  分天动线  三箭头体  杂志长条  时间轴体
红书种草  红书大纲  货架明细  包院私享  案例背书  抖音无营销
```

**旧名（改名前的同一批）：**
```
原生种草 → 红书种草      决策矩阵 → 红书大纲      抖音避坑 → 抖音无营销
```
旧键保留做向后兼容。存量 386 套 `文案.txt` 已把老三家移到**最前**。

版本名**不再截断到 4 字**（最长 5 字「抖音无营销」，此前被砍成「抖音无营」）。

### 4.4 `copyMissing`

```python
copy_missing = not copy_text                      # 文案.txt 没读出实质内容
# 平台槽位守卫 sanitize_platform_copy() 后：
#   copy_raw 且清洗后为空 / 不足 30 字 ⇒ copy_missing = True
```

阈值链：`MIN_COPY_DISTRIBUTABLE = 30`（整段）、`MIN_PLATFORM_SUBSTANCE = 30`（单槽位）。
四层守卫：字数 → 未填模板 → 平台槽位 → 有效长度。

`copyMissing=true` ⇒ 手机端**平台按钮置灰**，但作品仍然可见（文案缺失**不判废**，只有无图才判废）。

## 五、分类与排序

### 5.1 分类接口 `/api/online/categories`

共 **4 类**：

| 类型 | 生成逻辑 |
|---|---|
| 节日专题 | `🌕 中秋`（blob 含「中秋」）、`🇨🇳 国庆`（含「国庆」或「十一」），count>0 才出现，**置顶** |
| 游戏专题 | `🎮 游戏`，`is_game_work(rawTitle, path)` |
| 地域 | 遍历 `DESTINATIONS`（跳过中秋/国庆/游戏），有计数才出现，末尾追加「其他」，**按 count 倒序** |
| 已发次数 | 由 `/api/online/works?category=` 承担：`待首发`(==0) / `已发1次`(==1) / `已发2次`(>=2) |

⚠️ 分类靠 `work_text_blob`（title + 文案正文 + destination）做关键词匹配。
**一件作品在不在分类里，由「在不在 `已发送0次`」决定，与文件夹结构无关。**

## 六、更新中转（手机能升级全靠它）

手机连不上 GitHub ⇒ 电脑代取清单 + 安装包，改写 URL 后从局域网重发。**没有它手机永远升不了级。**

| 接口 | 说明 |
|---|---|
| `GET /latest.json`（含 `/altstore.json`） | 电脑代取发布清单，改写后返回；取不到返 503 |
| `GET /download/apk` | 返回 APK（`application/vnd.android.package-archive`） |
| `GET /download/ipa` | 返回 IPA（`application/octet-stream`）；失败返 502 |

- 上游：`https://raw.githubusercontent.com/zwmopen/gallery-updates/main/latest.json`，TTL 300 秒。
- 出网**多候选轮试**（DSH-115）：上次成功的 > env `DSH_UPDATE_PROXY` > 7897/7890/7891/7892 > 直连。
- 地址改写：`url`/`apk_url` → `/download/apk`，`ios.ipa_url` → `/download/ipa`。
- 🔴 **安装包缓存按 sha256 落名**（DSH-116）：GitHub 会以同一 `version_name` 重发**重新构建过**的包
  （字节不同、体积相同）⇒ 只按版本落名会让旧字节顶着新清单的 sha 被端出去，手机判废且**双方零报错**。

健康快照：`GET /api/online/status` → `updateRelay`（看 `manifestFetches` / `cachedVersion` / `cachedSha` / `shaMismatch`）。

⚠️ 已知：iOS 端**未发现**局域网中转消费点（`AlbumUpdateChecker.swift` 只有 GitHub 端点）。
