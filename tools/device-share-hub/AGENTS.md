# 分享中控维护规则

本目录是 Windows 素材投送中控、Android“相册”和 iPhone“相册”的同一产品源码。接手开发时不要另建替代项目，也不要恢复 Node.js 网页面板。

## 开始前必读

按顺序读取：

1. `docs/MAINTAINER_HANDOFF.md`：当前版本、架构、发布地址和下一步；
2. `README.md`：用户流程、产品边界和实机记录；
3. `docs/BUG_LEDGER.md`：已踩坑、根因和必须保留的回归；
4. `docs/TEST_PLAYBOOK.md`：自动测试、真机测试和证据记录；
5. 涉及协议或构建时再读 `docs/PROTOCOL.md`、`docs/SOURCE_BUILD_AND_RECOVERY.md`。

## 不可破坏的产品原则

- 在现有三端升级链上迭代，一个正式包兼容多台 Android/iPhone，不按机型分叉；
- 不增加手动 IP、配对码、命令行、管理员、ADB、Root、越狱、无障碍或设备管理等用户步骤；
- 手机主界面保持内容优先，低频入口收进设置；顶部顺序为传送、刷新、回收站、设置；
- 分享次数只代表用户点击了“复制并分享”，必须在点击边界立即且只记一次；不宣称目标平台发布成功；
- 不伪装系统相册来源、不伪造 EXIF、不绕过平台安全机制；
- 安装包不是源码备份，正式版本必须能从 Git 提交和工作流重建。

## 从用户角度审视（每次改代码前强制执行）

写完功能代码后、提交前，必须以真实用户视角过一遍以下清单。不是可选项 — 跳过这步就是"技术没问题但用户用着难受"的 bug 来源。

### 交互时效

- 用户执行操作后，1 秒内必须有视觉反馈（文字变化、进度条、动画），不能静默等待。
- 搜索/发现类操作超过 3 秒无结果时，必须显示"正在搜索…"而非空白。
- 错误超时不应超过 5 秒才给反馈。用户以为卡死了 = bug。
- 设备离线后，列表应在 60-90 秒内移除，不能让用户对着已经断连的设备操作。

### 操作步骤

- 常见任务（发文件给设备）的步骤数是否最少？能否减少一步？
- 多设备场景：用户有 8 台手机时，同一操作要重复 8 次吗？能否批量？
- 能否排队？用户传完一台想立刻排下一台，而不是干等。
- 用户切走窗口后回来，能否一眼看到当前状态（进度、成功、失败）？

### 信息可读性

- 错误提示是技术语言还是人话？把"错误 409"改成"手机上还有上一批没处理完"。
- 列表项有没有展示用户决策需要的信息（大小、时间、状态）？
- 用户能否分清"刚传过的"和"还没传的"？
- 空状态提示是否可行动？不要只说"未发现设备"，要说"请确认手机已打开相册并连接同一 WiFi"。

### 容错与恢复

- 用户误操作（拖错位置、点错按钮）会弹 MessageBox 打断流程吗？能否改为状态栏温和提示？
- 传送中断后，用户能否知道哪些传了、哪些没传？
- 大文件夹计算 SHA-256 时会不会卡住界面？长时间计算必须异步并显示进度。

### 日常体验

- 重启电脑后要手动打开吗？是否需要开机自启选项？
- 最小化后还有进度可见吗？传送完成有通知吗？
- 长时间使用是否刺眼？是否需要暗色模式？
- 多次操作产生的临时文件是否自动清理？

> 违反任何一条都应记录为 UX-BUG 并在本轮修复，不能留到下一版"再说"。

## 每次修改的收口要求

1. 同步修改代码、版本号、README、CHANGELOG/交接快照和相关测试；
2. 先跑自动测试，再按风险做实体设备操作；CI 成功和真机结果分开记录；
3. 未实际执行的操作只写为后续复核项，不扩大结论；
4. 失败记录按"现象 → 环境 → 根因 → 修复 → 证据 → 回归"写入 `docs/BUG_LEDGER.md`；
5. 发布前核对 EXE/APK/IPA、源码提交、Release、Android 更新索引和 SHA-256 一致；
6. 文档和日志禁止出现密码、Token、Cookie、Apple ID、设备唯一标识、配对记录、用户作品正文和原始隐私日志；
7. **提交前必须过一遍"从用户角度审视"清单**，发现 UX-BUG 立即修复或在 commit message 中说明延期理由。
